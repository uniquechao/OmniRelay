## 实施前核对

- 当前工作树已包含 C1–C3。交接三份文档位于项目主工作区的 `design/engineering/`。已核对其中的 P02、P07、CHAT04、PROJ03、联合验收 06，以及当前分支的聊天发送框和项目简报原型。
- `internal/chat/http.go` 可复用会话与现时成员校验。`chat.read_all` 是读取权限。`internal/chat/receipts.go` 已定义 E1 投递证据与 F1 权威业务回执的关联边界，`cmd/omnirelay/server.go` 有接入点。P02 首期建议采用 Bot 身份，真实开放仍需确认测试应用能力。项目侧沿用已定义的 F1 权威权限接口。
- 飞书普通文件用上传所得 `file_key` 发独立消息，正文与多个文件可能部分成功。当前 SDK 的发送 `uuid` 仅提供一小时去重，`Get` 按飞书消息 ID 查询。响应丢失且未获得消息 ID 时，需要明确可用于确认原操作的证据。
- 转系统规划，确定一次提交与各条飞书消息的持久化关系、部分成功的恢复语义、未知回执的确认条件，以及同一投递账本与简报授权和回执的接线。仅完成代码与契约核对，尚无实现或运行验证。

## 实施结果

- `internal/chat/delivery_http.go` 在 `/api/v1/feishu/chats/{chatID}` 下提供 `GET /send-capabilities`、`POST /attachments`、`POST /messages` 和 `GET /deliveries/{operationKey}`。提交使用 `operation_key`、`text` 或结构化 `paragraphs`，以及 `attachments` 中的上传引用。附件上传用名为 `file` 的表单字段，`kind=image` 走飞书图片接口，默认走飞书文件接口。引用有效期为 24 小时，绑定租户、应用、调用者、会话及凭据代次。
- `internal/chat/delivery.go` 仅使用 Bot 身份，对群聊复核 Bot、发布者及结构化 @ 对象的现时成员资格，1:1 复核本人绑定。正文和附件各生成一条飞书消息，开始投递前校验全部上传引用，随后逐条复核权限。成功表示飞书接受并返回可验证的消息 ID。按 P02，默认关闭真实发送，测试应用确认能力后可通过 `OMNIRELAY_FEISHU_BOT_SEND_ENABLED=true` 开启。
- `migrations/0011_feishu_deliveries.sql` 与 `internal/chat/delivery_store.go` 将操作键绑定到租户、应用、调用者、目标和内容指纹。逐条持久化状态及已确认的飞书消息 ID。同键查询或重复提交使用存量操作，核验证据可更新该操作的回执。投递中断后，已开始的部分保持未知，尚未开始的部分记录失败。若发送响应提供了与本次请求绑定的消息 ID，按该 ID、目标、消息类型和 Bot 身份核验。彻底丢失响应且无 ID 时保持未知。遇到部分成功保留已确认的证据。
- `SendBriefing` 让项目权威服务按正式简报回执、发布者、目标群和允许公开的内容授权，复用相同的发送服务。已确认的投递记录接入现有 `DeliveryReceiptSource`，聊天读取仍由正式业务回执来源复核读权限。
- 隔离 PostgreSQL 和受控飞书响应的定向回归通过，覆盖重复提交、错目标及附件错绑、上传失败、撤权前及投递中阻断、1:1、部分成功、响应丢失、原操作核验和旧数据库升级。真实租户收件及权限联验沿用 L2。
- 收尾自检补齐简报的独立状态查询权限。使用投递账本中的正式回执键向业务权威服务复核读权限，权限不足时拒绝查询。新增覆盖该撤权场景的断言，交系统门禁运行。
