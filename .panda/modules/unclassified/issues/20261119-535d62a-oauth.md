# #20261119-535d62a 隔离飞书 OAuth 限流额度，保障已发起登录的用户回跳

## 原始需求

cmd/omnirelay/server.go 对发起与回调各使用实例共享的固定窗口，回调在 internal/identity 的事务校验前计数。调整入口的限流设计，区分可信入口来源、无效回调和有效登录事务，限制压力并为合法回跳留出容量。核对部署入口的可信代理配置，保持对来源的可信校验，并保留 state、浏览器绑定、PKCE、一次性消费、站内回跳白名单和现有密码登录保护。

<!-- pandados:acceptance -->
- [ ] 隔离环境验证来自受限来源的请求不会阻断另一来源发起登录，持续无效的回调不会耗尽有效事务完成登录所需容量。整体容量仍有上限且被限流时提供可重试反馈。
- [ ] 未经可信代理证明的转发头不能改变限流归属。错 state、缺浏览器绑定、已消费 state、越权返回路径和异常回调保持原安全结果，成功和取消路径回归通过。

## 实施记录

- `internal/identity` 在 OAuth 发起处对可信来源和实例分别计数。回跳使用绑定浏览器和签发时间的签名，短期凭证和数据库记录沿用原有格式。普通无效回跳与升级前的事务共用受限的核验额度。已签名的回跳有独立的核验并发额度，已消费签名的短期缓存减少重复查询。
- 仅当数据库匹配未过期的登录事务后才扣减有效回跳额度。额度不足时回滚删除、保留浏览器绑定，并通过 HTTP 429 和 `Retry-After` 提供重试反馈。PKCE、单次消费和原有返回路径规则由登录流程继续校验。
- `cmd/omnirelay` 将正常登录限流移到身份服务。可信代理使用 TLS 连接与私有令牌，Go 仅在证明通过时采信 Nginx 覆盖的客户端地址。`deploy/k8s` 已记录私有入口配置要求，并加入可选 Secret 引用。当前工作区包含公开模板，目标主机的实际私有配置未在仓库中提供。

## 定向验证结论

- 隔离 PostgreSQL 和飞书测试替身验证通过。单个来源达到上限后，另一可信来源仍可发起；伪造转发头始终使用 TCP 对端的额度。无效回跳耗尽自身额度后，真实登录仍创建会话，真实取消仍返回登录页。回放与异常参数保持原有安全结果。
- 验证实例发起上限和有效回跳限流重试。有效回跳收到 429 后未消费数据库事务，也未清除浏览器绑定；窗口重置后可完成原事务。现有 PKCE、并发单次消费、返回路径授权、密码登录及 Web 初始化回归通过。
- Kubernetes 模板的 Secret 引用和部署脚本语法已核对。索引无已登记模块，本 issue 归类为 `unclassified`，没有模块文档可更新。长期部署配置说明已写入 `deploy/k8s/README.md`。
